# 0002 — Manufacturing order identity and source of record

## Status

Accepted — 2026-06-02.

## Context and problem statement

NSG-17 implements `POST /api/v1/orders/` (serializer + `create_order` use case that
emits `orders.created`). To freeze the request/response contract we must first decide
how a manufacturing order (OF) is identified externally, and whether the endpoint must
enforce an `idempotency_key`.

Two forces pull in opposite directions:

1. SAP is the inbound source of production orders (`docs/architecture/integrations/erp-sap.md`),
   with an anti-corruption layer in `apps/orders/infrastructure/sap/`. GP-008 requires an
   `idempotency_key` on any endpoint that ingests data from an external system.
2. The same endpoint is also expected to support manual creation from the UI, where there
   is no ERP order number and forcing an `idempotency_key` would be awkward.

The order identifier and the (non-)mandatory nature of `idempotency_key` are **irreversible
schema decisions**: changing them once production data exists requires a migration plus
reprocessing of the SAP integration. `docs/product-specs/orders/README.md` listed this as an
open TODO; ADR 0001 does not resolve order identity. This decision was escalated via the
Question ticket NSG-44.

## Decision drivers

- **Irreversibility.** The primary key and identity strategy are hard to change with live data.
- **Decoupling from SAP.** Order identity should not be hostage to an external system's numbering.
- **GP-008 compliance.** External ingestion must stay idempotent without blocking manual UI creation.
- **Dual source of creation.** Both ERP ingestion and manual UI creation must be first-class.

## Considered options

### A) Internal identifier (UUID or sequential) generated by the MES

Pros:
- Simple contract, fully decoupled from the ERP.
- No `idempotency_key` required for the manual path.

Cons:
- Clashes with SAP being the source of production orders.
- Correlation with the ERP order number is left unresolved.

### B) ERP-provided order number, sent and unique in the body

Pros:
- Aligns directly with `erp-sap.md`.
- Treated as external ingestion → `idempotency_key` mandatory (GP-008) + duplicate validation.

Cons:
- Requires an ERP order number to always exist.
- Complicates (or blocks) manual creation from the UI.

### C) Hybrid: stable internal UUID PK + optional `external_order_ref` for ERP correlation ← **chosen**

Pros:
- Least irreversible: identity is owned by the MES, not by SAP.
- Supports both the UI path and the ERP ingestion path.
- `idempotency_key` required only when the request source is the ERP.

Cons:
- Requires the endpoint to distinguish the request origin (manual UI vs. ERP ingestion).

## Decision outcome

**Option C.** A manufacturing order is identified by a **stable internal UUID primary key**
generated by the MES. An optional `external_order_ref` field holds the ERP order number for
correlation when the order originates from SAP. The order identity is never coupled to SAP.

The `idempotency_key` requirement (GP-008) is applied **conditionally on the request source**:
it is mandatory when the order is ingested from the ERP and is not required for manual creation
from the UI. The endpoint must therefore distinguish the origin of the request.

### Positive consequences

- Order identity is owned by the MES and stable regardless of ERP behaviour.
- Both manual UI creation and ERP ingestion are supported by a single resource.
- GP-008 is preserved for the ERP path without blocking manual creation.

### Negative consequences

- The endpoint must distinguish request origin (manual vs. ERP) to apply the right rules,
  adding branching to the serializer / use case.
- `external_order_ref` correlation logic and its uniqueness scope must be specified
  (follow-up in `docs/product-specs/orders/`).

## Pros and cons summary

Option C wins on irreversibility: a MES-owned UUID avoids binding identity to SAP, while an
optional `external_order_ref` plus source-conditioned idempotency keeps GP-008 intact without
blocking manual creation. It is the lowest-irreversibility path among the three.
